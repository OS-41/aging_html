# aging_html

Webカメラで撮影した画像をaging APIに送り、生成結果を表示する展示物。

## 画面

| パス | 用途 |
| --- | --- |
| `/capture.html` | 撮影ブース。写真を送って受付番号を渡すまで |
| `/view.html` | 閲覧ブース。係員が入れ替えるまで同じ内容を映し続ける |
| `/staff.html` | 係員用。表示の切り替え・保管一覧・処理履歴 |
| `/` | 設営用の案内(上の3つへの行き先だけ) |

ブラウザからaging APIを叩く経路は置いていない。生成の依頼はすべて
`POST /api/entries` を通り、サーバー側だけがaging APIと話す。
入口が1つなので、利用枠を使う操作も受付の上限(`MAX_ENTRIES`)の中に収まる。

### 2ブース構成の流れ

撮影ブースと閲覧ブースは別の端末で、間に10分以内の移動時間が挟まる。
来場者は撮影した順に閲覧ブースへ到着するため、撮影時刻順の待ち行列として扱う。

1. 撮影ブースが `POST /api/entries` で写真を送り、受付番号を受け取る
2. サーバーが裏でaging処理を進める(移動時間がそのまま生成時間になる)
3. 完成した結果画像をサーバーのディスクに取り込む
   — aging API側のURLが短時間で失効しても閲覧ブースで表示できるようにするため
4. 係員が `/staff.html` で「結果画面に移行」を押すと、未表示のうち古い順に
   まとめて閲覧ブースへ出る。閲覧ブースは画面を人数分に区切って並べる。
   「待機画面に移行」で背景の演出だけの画面へ戻す

一度に表示する人数は `server.js` の `DISPLAY_SLOT_COUNT` で決める(既定は6人)。
撮影も6人ずつまとめて行う前提。

受付は30分(`ENTRY_TTL_MS`)、アップロードされた元画像は生成完了時点で削除される。

取り込む結果画像は、閲覧ブースで見せる1枚だけ(`server.js` の
`SAVED_RESULT_AGE`、既定は70歳)。ディスクと取り込み時間が枚数ぶん減り、
1枚の取得失敗が受付ごと失敗させる範囲も狭くなる。
**`SAVED_RESULT_AGE` を `null` にすると、APIが返した全年齢を取り込む**
(以前の動作)。複数年齢を見せる仕様に戻すときはここを戻す。
`view.html` の `DISPLAY_AGE` と値を合わせること。

### 入口の守り(Basic認証)

公開パス(`APP_BASE_PATH`)配下のすべてにBasic認証をかける。
外に開いているのは `GET /healthz` と `GET /files/:file_id` だけ
(前者は認証と公開パスの外、後者はaging APIが元画像を取りに来るため)。

資格情報の比較は `safeEqual()` で長さの差も含めて一定時間で行う。
文字ごとに応答時間が変わると、1文字ずつ当てられてしまうため。

**認証の失敗は接続元ごとに数える。** 10分のあいだに20回失敗した接続元には、
以後の失敗への応答を2秒遅らせる(`AUTH_FAIL_LIMIT` / `AUTH_FAIL_DELAY_MS`)。
最初の1回と5回ごと、そして遅らせ始めたことを処理履歴に残すので、
入口を叩かれていることが係員画面で分かる。

**正しい資格情報は、失敗が続いたあとでも必ず通す。**
締め出す作りにすると、係員が打ち間違えたときに自分たちが入れなくなる。
正しい値を知っている相手を止めても意味がないため、遅らせるのは
間違えた側だけにしてある。成功すると数え直す。

資格情報を送ってこない最初の401は数えない(ブラウザが必ず出す普通の流れ)。

どの応答にも次のヘッダーを付ける。

| ヘッダー | 目的 |
| --- | --- |
| `Strict-Transport-Security` | 以後HTTPSでしか繋がせない(公開時のみ)。Basic認証は毎回資格情報を送るため、平文で出す機会を作らない |
| `Referrer-Policy: no-referrer` | 外部への通信に参照元URLを載せない。公開パスを外へ渡す機会を作らない |
| `X-Content-Type-Options: nosniff` | 中身から型を推測させない |
| `X-Frame-Options: DENY` | 他所のページの枠に埋め込ませない |

`X-Powered-By` は消す。版に紐づく既知の弱点を探す手間を減らすだけの情報で、
こちらが得るものは何も無いため。

Renderはプロキシの後ろでアプリを動かすため `trust proxy` を1段だけ立てる。
立てないと全員が同じ接続元に見え、1人の総当たりでブースまで巻き込む。

**他所のページから引かれた状態変更は断る(CSRF対策)。**
Basic認証は、一度通したブラウザが以後すべての要求に資格情報を自動で付ける。
そのため係員画面を開いたままの端末で別のページを踏むと、そこに置かれた
`<form action="…/api/display/advance">` が資格情報つきで送られ、
来場者の目の前で画面が切り替わってしまう。本文の要る操作は
`express.json()` が弾くが、`advance` と `clear` は本文が要らない。

`GET`/`HEAD`/`OPTIONS` 以外の要求では `Sec-Fetch-Site` を見て、
`same-origin` と `none`(アドレス欄・ブックマーク)以外を403で断り、
処理履歴に `request:cross-site` として残す。この値はブラウザ自身が付け、
ページ側から書き換えられない。ヘッダーが無いもの(curlや古いブラウザ)は通す
——狙いはブラウザ経由の誘導だけで、そこは会場で使う端末すべてが対応している。

鼓動を覚えておくブースの数には上限を置く(`MAX_CLIENTS` = 32)。
`client_id` はブラウザが名乗るだけの値で、毎回違う値を送られると表が
いくらでも膨らむため。溢れたら最も長く音沙汰のないものから捨てる。

### キオスク化と掲示

撮影ブース・閲覧ブースは `body.is-kiosk` を付けて、来場者が画面に触れても
表示が崩れないようにする(`lockKiosk()` / `booth.css`)。係員画面には付けない
(文字を選べ、拡大できる必要があるため)。

| 止めるもの | 手立て |
| --- | --- |
| 文字の選択・長押しのメニュー | `user-select: none` / `-webkit-touch-callout: none` / `contextmenu` |
| ダブルタップでの拡大 | `touch-action: manipulation` ＋ 同じ場所を続けて叩いたときの `touchend` |
| ピンチでの拡大 | `gesturestart` など(iOSのSafariは `user-scalable=no` を無視する) |
| 引っぱりでの移動・スクロール | `overflow: hidden` / `overscroll-behavior: none` / 2本指の `touchmove` |
| 写真の持ち出し | `-webkit-user-drag: none` |

**画面はスクロールしないので、1画面に収まりきることが前提になる。**
カメラ映像の枠(`.stage`)は固定の高さを持たず、見出し・掲示・ボタンを置いた
あとの残り全部を使う。固定にすると縦の短い端末でボタンが画面の外に出て、
スクロールも止めているため押せなくなる。

**縦が900px以下の画面(iPadの横向きなど)では、周りをひと回り小さくする**
(`@media (max-height: 900px)`)。主役はカメラ映像なので、見出し・掲示・
ボタン・係員向けの行を詰めて、空いた分を映像に回す。
係員向けの行は1行に収める(折り返すとそのぶん映像が縮むため、
背景合成の状態は幅を決めて末尾を畳み、控えめなボタンは本来の幅に戻す)。
これで1180×820のとき映像の枠は483px取れる(詰める前は290px)。

**開発モードのときだけは画面を送れるようにする**(`body.is-dev`)。
開発モードの操作欄まで入れると画面の高さに収まらないことがあり、
送れないと見切れたまま届かなくなるため。使うのは係員だけ。

端末側でも全画面表示・スリープ無効・自動再起動の停止を設定すること。

撮影ページの見出しの下に、個人情報の扱いを常時出す(`.privacy`)。
外部サービスへ送ること、元の写真は加工後すぐに・加工後の写真も最大30分で
消すこと、他の目的には使わないこと。撮る前に目に入る位置に、立ったまま
読み切れる長さで置く。

### 撮影ブースの送信と撮り直し

「この写真を送る」を押してから受付番号が出るまでの間は、撮影した写真の上に
処理中のおおいを重ねる。来場者が「押せたのか分からない」「固まった」と
誤解して二度押しするのを防ぐため、この間は操作できるボタンを出さない。

送信のあと、8秒だけ `GET /api/entries/:id` を見張る(`CONFIRM_WINDOW_MS`)。
aging APIが顔を認識できない場合はこの間に `status: error` になるため、
来場者がまだブースにいるうちに撮り直してもらえる。生成そのものの完了は
待たない(移動時間を生成に充てるのが2ブース構成の前提のため)。

失敗した場合は撮り直しの案内を出し、25秒後には自動で撮影画面へ戻る
(`FAILURE_RESET_MS`)。来場者がその場を離れても次の人が使えるようにするため。
この8秒を過ぎてから生成が失敗した場合は撮り直しを促せないため、係員画面の
処理履歴に `entry:error` として残る。

失敗の見せ方は2種類ある。**来場者が撮り直して直せるものだけ**に姿勢の指示を
出し、それ以外はすべて技術的な問題として扱う。

| 種類 | 大きく出す1行 | 次にしてほしいこと |
| --- | --- | --- |
| 撮り直しで直る | 「少しあごを引いてください」など具体的な指示 | もう一度撮影してください |
| 技術的な問題 | 技術的な問題が発生しました | 係員をお呼びください(係員は管理画面の処理履歴を見る) |

振り分けは `capture.html` の `IMAGE_ERROR_MESSAGES` に載っているかどうかで決まる。
載っているのは立ち位置・顔の向き・写り方に関する19種のみ。
**表に無いコード、コードが取れなかった場合、送信そのものの失敗は、すべて
技術的な問題**として扱う。

以前は未知のコードにも姿勢の指示を出していたため、**APIユニットが尽きたときに
来場者が何度も撮り直す**状態になっていた。原因が分からない失敗に対して
来場者へ指示を出さない、というのがこの振り分けの主旨。

どちらの場合も、案内の下に受付番号と実際のコード・エラー文を小さく出す。
係員が姿勢の問題と基盤の不調を、履歴を見に行かずに切り分けられるようにするため。

技術的な問題のエラー文はサーバーが `describeAgingError()` で組み立てる。
aging APIが返すコードとHTTPステータスに日本語の説明を添えるため、
係員は履歴の1行だけで対処が分かる。

| 返ってくるもの | 添える説明 |
| --- | --- |
| `CreditInsufficiency` | APIのユニットが不足しています(追加購入が必要) |
| `InvalidParameters` | リクエストの内容が不正です |
| `BadRequest` | 想定外のリクエスト内容です |
| `InvalidStyleGroup` / `InvalidStyle` | スタイル(グループ)IDが不正です |
| HTTP 400 | リクエストが不正です(task_idの誤りを含む) |
| HTTP 401 | APIキーが無効です |
| HTTP 429 | リクエストが多すぎます(レート制限) |
| HTTP 500 | aging API側で処理が時間切れになりました |

ユニット不足と鍵の誤りとレート制限は対処がまるで違うため、
`aging:start` の失敗はこの1行を処理履歴と通信状況の両方に残す。

### 本日の受付終了

1日の上限に達したら、**撮影ブースと閲覧ブースの両方**に「本日は終了しました」と
出す。締め切り方は2つあり、どちらか一方でも成立していれば終了になる
(`server.js` の `serviceIsClosed()`)。係員画面の「表示の制御」から操作する。

| 締め切り方 | 操作 | 何が起きるか |
| --- | --- | --- |
| 強制終了 | 「本日の受付を終了する」(確認あり) | 押した時点で終了。閉場・機材の不調・時間切れ用 |
| 人数上限 | 上限を入れて「この人数で数え始める」(確認あり) | **入れた時点から**受け付けた人数を数え、達した時点で終了 |

数え始めを「入力した時点」にしてあるのは、前日の試写や当日朝の試運転まで
来場者ぶんとして数えてしまうと、実際に通せる人数が減ってしまうため。
**上限を入れ直すたびに0人から数え直す。**

締め切ると、撮影ブースはカメラを止めて掲示だけになる。サーバーも
`POST /api/entries` を409で断る(掲示を見る前に押されたぶんを、上限を超えて
受け取らないため)。ここで来場者は増えなくなる。

**閲覧ブースが掲示に変わるのは待機画面のときだけ。** 締め切ったあとも、すでに
撮り終えて移動中の人が残っている。その最後の組を係員が出しきれるよう、
「結果画面に移行」は今までどおり使え、結果を出している間は写真を並べる
(玉手箱の演出もそのまま出る)。出し終えて待機画面に戻した時点で掲示に変わる。

「本日の受付を再開する」で戻す。上限に達して止まっていた場合は、再開と同時に
0人から数え直す(そうしないと、再開した瞬間にまた終了してしまう)。
撮影ブースは「カメラを開始」からやり直しになる。

締め切りの状態は**再起動で消える**(受付や結果と同じ)。会場で再起動が要る
事態になったら、係員が入れ直す。出入りはすべて処理履歴に残る
(`service:closed` / `service:open` / `service:limit`)。

### 撮影ブースの背景合成

人物だけを切り抜いて背景の上に重ねた映像を撮影する。
背景には閲覧ブースの待機演出と同じ絵(`public/ocean-scene.js`)を使うため、
撮った写真の中の世界と、この先で見る画面の世界が揃う。

切り抜きにはMediaPipeのSelfie Segmentationを使い、スクリプトは
cdn.jsdelivr.net から読み込む。**会場のネットワークがこのCDNへ到達できるか
事前に確認すること。** 読み込めない場合は自動でカメラ映像そのままの撮影に
切り替わり、展示は止まらない(その旨は係員画面の処理履歴に残る)。

**このURLには版を指定していない(`capture.html` の `CDN`)。**
つまり当日読み込まれるのは、その時点で最新として公開されている版になる。
カメラ映像を扱っているページで動く他所のコードなので、当日までに
`@mediapipe/selfie_segmentation@<版>` の形で版を固定するのが望ましい。
できれば `public/vendor/` に置いて自前で配信すると、CDNへの到達も
版の変化も当日の心配事から外れる(`locateFile` の行き先も合わせて変える)。

使うカメラは撮影ブース画面下部で選べる。USBカメラを繋いでも内蔵カメラが
選ばれることがあるため。選んだカメラは端末のブラウザに記憶され
(`localStorage`)、撮影・送信・「次の人へ」やページの再読み込みをしても
選び直す必要はない。記憶した機器が外れていた場合は既定のカメラに戻し、
その旨を処理履歴に残す。

背景は撮影ブース画面下部で切り替える。

| 選択肢 | 背景 |
| --- | --- |
| 絵本のわく | `backgrounds/aging_captureBackground.webp`(既定、1654×951)。中央が空いた水彩の枠 |
| 閲覧ブースに合わせる | 係員が選んでいる絵柄に自動で追従する |
| 海の中 / 絵本の海 / 水彩の絵本 | 絵柄を固定する |
| 静止画(海の中) | `backgrounds/ocean.svg` |
| 背景なし | カメラ映像そのまま |

閲覧ブースが `tamatebako` のときは人物を重ねる構図ではないため、
「閲覧ブースに合わせる」では `picturebook` に読み替える。

演出はカメラのフレームと同じ縦横比で、長辺960px・毎秒30コマまでに抑えて
描いている(`capture.html` の `SCENE_MAX_SIDE` / `SCENE_FRAME_MS`)。
撮影ブースの端末が重いときはこの値を下げるか、静止画に切り替える。

### 閲覧ブースの2つの画面

閲覧ブースは係員が2つの状態を切り替える。サーバーが状態を保持するため、
閲覧ブースを再読み込みしても戻らない。

| 状態 | 画面 | 係員の操作 |
| --- | --- | --- |
| `waiting` | 背景の演出だけ。結果の区画も枠も出さない | 「待機画面に移行」 |
| `results` | 届いている人数ぶんの区画に結果を並べる | 「結果画面に移行」 |

**出す人数は自動で決まる。**「結果画面に移行」を押すと、まだ表示していない
受付を撮影の古い順に**最大 `DISPLAY_SLOT_COUNT`(6)人**まで取る。
未表示がそれより少なければ、その人数ぶんだけを並べる(4人なら4枚で画面を
使い切る。空き区画は作らない)。係員画面のボタンには次に出る実際の人数が出て、
0人のときは押せない。

区画の並びは人数で決まる(`rowsFor()` / `applyLayout()`)。

| 人数 | 並び |
| --- | --- |
| 1 | 段に分けず、画面いっぱいに1枚 |
| 2 | 段に分けず、左右に1枚ずつ(画面が横長なので、縦に積むより大きく出せる) |
| 3 | **2** + 1 |
| 4 | 2 + 2 |
| 5 | **3** + 2 |
| 6 | 3 + 3 |

奇数のときは上段が1枚多い。段ごとに枚数が違うため、格子(grid)ではなく
段を横並びの箱(`.slot-row`)にして、それぞれ中央に寄せている。
区画の大きさは枚数の多い段を基準に決め、両段で同じ大きさにする。

aging APIは複数の年齢を返すが、閲覧ブースでは1枚だけを大きく見せる。
どの年齢を出すかは `view.html` の `DISPLAY_AGE`(既定は70)で決める。
該当する年齢が無ければ最も近いもので代える。

区画は写真そのもので、番号と年齢は写真の上に重ねる。撮影ブースから送るのは
カメラのフレーム(横長)なので結果も横長で返る。横長の区画に `object-fit:
contain` で収めることで、切り取らずにほぼ全面を使う。展示用の大画面では
遠くから見えないと意味がないため、元の解像度より大きく引き伸ばすことは許す。

`booth.css` の `.booth { max-width: 900px }` は手元で読む画面向けの値なので、
閲覧ブースでは `view.html` 側で打ち消している。これがあると
2560×1600 や 2360×1640 のディスプレイでも結果が中央の900pxに押し込められる。

区画の並べ方は `applyGrid()` が毎回計算する。正方形に近い分割ではなく、
**写真がいちばん大きく収まる列数**を選ぶ。結果が横長なので、区画が正方形に
近いと上下が余るため。最適な列数は画面の形で変わり、6人なら
MacBookは3列×2段、iPadは2列×3段になる。
区画の実寸も写真と同じ形にして、余白が白い帯として見えないようにしている。

縦横比は最初 16:9 を仮定し、実際の画像が届いた時点でその値に直して
並べ直す(`adoptPhotoAspect()`)。APIの出力が横長でなくなっても追従する。

想定する実機はMacBook Pro(2560×1600)とiPad(2360×1640)。いずれもRetinaで
CSS上は約1512×945 / 約1180×820になる。6人表示でのこの2つでの実測は
475×267 / 392×220。

### 閲覧ブースの待機演出

背景の演出は `prefers-reduced-motion` が有効な環境では静止した1枚だけを描く。
絵柄は4種類あり、係員画面から切り替える(仮運用)。

| 値 | 絵柄 |
| --- | --- |
| `realistic` | 実際の海中に近いもの。暗い水色、光の筋、影のような魚 |
| `storybook` | 童話の絵本のようにデフォルメしたもの。太い輪郭線と平坦な色面、大きな目の魚、砂地と海藻 |
| `picturebook` | 水彩の絵本のような額縁。中央を白く空け、縁にクジラ・ウミガメ・カクレクマノミ・タツノオトシゴ・カニ・珊瑚を配する。この絵柄のときは画面全体が明るい配色に切り替わる |
| `tamatebako` | 浜辺と玉手箱の絵(`backgrounds/aging_viewBackground.jpg`、1195×896)。雲の部分に結果を並べ、入れ替えのたびに煙の演出が入る |

#### 玉手箱の演出

`tamatebako` のときだけ、「結果画面に移行」を押すと次の流れが走る
(`public/tamatebako-scene.js`、全体で約7.8秒)。

見せ方の要は**煙で埋め尽くしてから中身を入れ替え、煙が晴れる中で結果が
現れる**こと。順に、①玉手箱を開ける → ②煙を画面いっぱいに(背景はまだ
替えない・結果も出さない) → ③覆われている隙に背景を煙ありの絵へ替える →
④結果を煙の下に置く → ⑤煙が晴れる、となる。
結果そのものを淡く出し入れはしない(区画に不透明度の遷移をかけない)。
隠すのは煙だけの仕事にしてあるため、見え始めるのは煙が薄れるからになる。

待機中は玉手箱が閉じていて、煙は出ていない。

ふたの開き具合は**背景の絵そのものを差し替えて**見せる。`#backdrop` に絵を
重ねて置き、不透明度で入れ替える(`setBackdrop()`)。canvasが描くのは煙と、
口から漏れる光だけ。以前はcanvasでふたを描いていたが、絵に描かれた玉手箱と
馴染まなかったため、絵を用意してもらう方式に変えた。

| 層 | ファイル | 使いどころ |
| --- | --- | --- |
| `closed` | `aging_viewBackground_closed.jpg` | 待機中。ふたが閉じていて煙もない |
| `opened` | `aging_viewBackground_opened.jpg` | ふたを開けた直後。まだ煙が出ていない |
| `smoke` | `aging_viewBackground.jpg` | 煙が出てからずっと |

どの絵も同じ寸法・同じ構図であること(現在はいずれも1195×896)。
用意していない層を指定した場合は何も変えないため、絵が揃っていなくても
演出は止まらない(その層を飛ばして次へ進む)。

| 段階 | 長さ | 画面 |
| --- | --- | --- |
| `lifting` | 2.0s | ①`opened` の絵へ入れ替わる。煙はまだ出さない |
| `rising` | 1.0s | ②口から最初のひと筋が立ちのぼる。背景は `opened` のまま |
| `filling` | 1.4s | ②煙が画面いっぱいに広がる。終わりぎわに一面を塗り足す |
| `veiled` | 1.2s | ③背景を `smoke` へ替え、④結果を煙の下に置く |
| `settling` | 2.2s | ⑤煙が薄れ、下の結果が見えてくる。広がりは保ったまま |

`veiled` が1.2秒あるのは、背景の入れ替えに0.8秒かかるため。
入れ替えが終わるまで覆われたままになる長さにしてある。

かたまりの煙だけでは隙間が残るので、`filling` の終わりから `settling` まで
**一面を塗りつぶす層**(`drawVeil()`)を重ねる。これが1のあいだに背景と結果を
入れ替えるため、入れ替えの瞬間が見えることはない。
`settling` では**一面の層を先に(前半55%で)引き、かたまりの煙を最後まで残す**。
両方を同じ速さで薄めると終わりぎわまで真っ白のままになり、結果が急に
現れて見えてしまうため。区画ごとに晴れ方が違うのは、かたまりの位置による。

**煙は演出の間だけ写真より手前に置く**(`#ocean.is-front`)。
覆っている間に写真が煙の上に出ていると透けてしまうため。
`settling` で濃さを0まで落としきり、`done` で煙を写真の後ろへ回してから、
漂う煙を1秒かけて戻す(`SETTLE_FADE_MS`)。
前に出したまま漂わせると、結果の写真が白くかすんでしまう。

いちど出した煙は「待機画面に移行」まで消さない。戻すときは
`tamatebako-scene.js` の `close()` で煙が薄れ、入れ替わりにふたが閉じる。

③④は `veiled` だけに任せず、それ以降のどの段階を受け取っても行う。
描画が飛んだときに背景も結果も出ないまま演出が終わるのを防ぐため。

背景画像を差し替えたら、`tamatebako-scene.js` の `BACKDROP`(元の寸法)と
`BOX_IN_IMAGE`(絵の中での玉手箱の位置)も合わせること。
煙の出どころと光の位置がこれで決まる。

背景は `#backdrop` に `background-size: cover` / `background-position: center`
で敷く。煙の出どころと閉じたふたの位置は、画面に対する割合ではなく
**絵の中での位置**から毎回計算する(`tamatebako-scene.js` の `BACKDROP` と
`BOX_IN_IMAGE`)。coverでは画面の縦横比によって絵のどこが切り取られるかが
変わるため、画面基準で固定すると別の縦横比のディスプレイで玉手箱からずれる。

**背景画像を差し替えたら `BACKDROP`(元の寸法)と `BOX_IN_IMAGE`(絵の中での
玉手箱の位置と横幅)を合わせること。** 現在の値は 1195×896 の絵に対するもの。
海中の3絵柄の描画は `public/ocean-scene.js` にまとめてあり、閲覧ブースの
待機演出と撮影ブースの背景合成で共有する。絵柄を足す場合は、このファイルの
`themes` に描画関数を追加して `OCEAN_THEMES` に名前を足し、
`server.js` の `DISPLAY_THEMES`・`staff.html` と `capture.html` の
`<select>` に値を足す。

### 係員画面の操作

`/staff.html` には4つの欄(表示の制御・通信状況・保管中の写真・処理履歴)を
**縦の列に積む**。列の中では上から詰まるので、隣の列の欄が縦に長くても
下に空きができない。**列の数は上の「横に◯列」で1〜4から選ぶ**
(狭い画面では列が縦に積まれる)。

**各欄は見出しを押すと開閉**、**右上の「⠿ 移動」をつまむと並べ替え**、
**下端のつまみを上下にドラッグすると高さを変えられる**。
並び・列数・高さはまとめて端末に記憶される(`aging-staff-layout`。
再読み込みしても戻らない)。「並びを初期化」で既定の2列に戻せる。

並べ替えも高さの変更も、マウスでも指でも同じ操作になるよう
Pointer Events で扱う。実装で気をつける点が2つある。

- **つまみを `<summary>` の中に置かない。** `<summary>` の中の操作要素は
  ブラウザによって扱いが違い、押しても開閉だけが起きてつまみとして
  働かないことがある。欄(`<details>`)とつまみは `.panel-shell` がまとめ、
  つまみは殻に対して絶対位置で重ねる(畳んだ欄でも移動できる)。
- **動かしている間の `pointermove` / `pointerup` は `window` で受ける。**
  `setPointerCapture` に任せると、つまみから指が外れた時点で動きが
  届かなくなるブラウザがあり、つまんでも何も起きない。
  捕捉には頼らない(捕捉が使えない環境でも同じように動く)。
- **マウスイベントからも同じ流れに入れる。** Safari(macOS)では
  `pointerdown` で `preventDefault()` しても続く `mousedown` が止まらず、
  文字列の選択やブラウザ自身のドラッグが始まってしまう。そちらに
  持っていかれると `pointercancel` が飛んで動かせなくなるため、
  `mousedown` 側でも `preventDefault()` し、`mousemove` / `mouseup` でも
  同じ処理を呼ぶ。マウスの `pointercancel` は無視する(指の操作のときだけ
  取りやめる)。つまみには `user-select: none` と `draggable="false"` も付ける。

つまみを押すと、動かす前でもつまみの色が変わる(`is-grabbed`)。
「掴めていないのか、掴めているが動かせないのか」を切り分けられるようにするため。

**指でも同じように動かせる**(iPadでの操作用)。つまみには `touch-action: none`
を付け、押したところから指を滑らせるだけで運べる(長押しは要らない)。
画面の端まで運ぶと**そのまま画面が送られる**(移動のときだけ。高さの変更では
基準がずれるので送らない)。欄の全体が画面に収まらない縦向きの端末でも、
画面の外にある位置へ運べるようにするため。

通信状況の欄には**いま動いているサーバーの版**(Renderが渡すコミットID)を出す。
直したはずの動きにならないとき、古いビルドを見ていないかをここで確かめられる
(ローカル実行では「不明」と出る)。

つまんだまま動かすと、**近くの欄に隣り合う位置に吸い付き、そこが青い印で
示される**。離すとその位置に入る。列をまたいでも運べ、空の列にも置ける
(空の列は破線の枠で場所を示す)。6px動かすまでは始まらないので、
押しただけで並びが変わることはない。つまみにフォーカスして矢印キーでも
動かせる(上下は同じ列の中、左右は隣の列の同じ高さへ)。Escapeで取りやめ。

**高さを決めた欄は、その高さのまま。**中身が増えても縮んでも欄は伸び縮みせず、
入りきらない分は欄の中を送って見る。送るのは `<details>` 自身にさせている。
`<details>` の中身はブラウザが `::details-content` という箱で包むため、
中の要素に `flex` を指定してもその箱には効かず、中身が欄からはみ出してしまう。
見出しは送っても残るように貼り付けてある(`position: sticky`)。下限は120px。
**つまみを2回押すと、決めた高さを捨てて中身に合わせた高さに戻る。**
畳んだ欄には高さを当てない(背の高い空き箱が残らないようにするため)。
高さを決めていない欄は、表ごとの `max-height` で高さを抑える。

**サーバーが再起動すると、画面の上に赤い通知が出る。**
起動時刻(`/api/status` の `server.started_at`)が変わったかで見ている。
再起動をまたぐと保管中の受付も結果画像も消え、受付番号(`entrySequence`)も
1番に戻るため、黙って消えると係員には「番号が呼ばれない」としか見えない。
通知は押して消すまで残り、処理履歴にも `server:restarted` として残る。
番号が1番に戻ることで新しい写真の通知が止まらないよう、
このとき `lastSeenSequence` も戻す。

保管中の写真は1件ずつ削除できる。押すと確認のダイアログが出る。
**削除すると元画像も結果画像も戻せない**ため。

ファイル名は既定で1行に畳み、入りきらない分は末尾の「…」にする。
行の右の「⋯」を押すと全文(1件ずつ改行)に切り替わる。
名前が長いせいで表が横に伸び、番号や状態が読めなくなるのを防ぐため。
開いたかどうかは受付ごとに覚えるので、3秒ごとの更新では閉じない。

「更新を無効にする」を押すと、閲覧ブースの入れ替えを受け付けなくなる。
会場での調整中に誤って画面を変えてしまうのを防ぐための鍵で、これも確認の
ダイアログが出る。無効の間は `POST /api/display/advance` と `/clear` が
サーバー側で409を返すため、係員画面のボタンを迂回しても変えられない。

### 開発モード

aging APIのユニットが尽きている間や、設営中でまだ誰も撮影していない間でも
各画面を確認できるよう、係員画面から**開発モード**に入れる。出入りには
どちらも確認のダイアログが出る(本番の表示に見本が混ざると、来場者が自分の
写真を探せなくなるため)。

開発モード中に変わるのは次の2点だけで、それ以外の動作は本番と同じ。

- **結果画面を見本で埋められる。** 有効な撮影結果が1件も無くても
  「結果画面に移行」が通り、足りない区画は `GET /api/dev/placeholder/:index`
  が返すSVGで埋まる。aging APIは呼ばず、ディスクも使わない。
  見本の区画は黄色い破線と「番(見本)」の表示で本物と区別できる。
  **何人分で埋めるかを1〜6から選べる**(係員画面の「見本で埋める人数」)。
  本番は届いた人数ぶんだけを並べるので、人数ごとの並びを確かめるには
  これが要る。
  **撮影した写真はaging APIに送らず、そのまま閲覧ブースに出す。**
  `processEntry()` の頭で折り返し、元の写真を1枚だけ持つ `ready` にする
  (`keepOriginalAsResult()`)。**ユニットを1つも使わずに**、撮影から閲覧までを
  実際の写真で通せる。生成を待たないので受付から表示可能まで数十ミリ秒。
  元の写真は `results/` へ複製して受付と寿命を揃える。
  閲覧ブースでは赤い破線と「番(未加工)」「加工前の写真」で、係員画面では
  「未加工」の札で区別する。**開発モードを終了すると、この受付はまとめて
  削除される**(加工されていない写真が「未来のあなた」として残らないように)。
  **見本が出るのは未表示の受付が1件も無いときだけ。** 受付があるときは
  開発モードでも本番とまったく同じ人数・同じ並びで出す(見本で水増しすると、
  本物の写真が出ているときの見え方が変わってしまうため)。
  係員画面のボタンも、そのときどちらが出るかに合わせて
  「次の3人」「見本4人」と出し分ける。
- **撮影ブースに状態を選ぶ欄が出る。** 撮影前・撮影後の確認・送信中・
  お顔の確認中・受付完了に加えて、撮り直しの案内19種と技術的な問題22種を
  その場で表示できる。選んでも受付は作らず、写真も送らない。
  選択肢は `IMAGE_ERROR_MESSAGES` と `DEV_TECHNICAL_CASES` から組み立てるため、
  表に手を入れれば選択肢も増える。

開発モード中は閲覧ブースの右上と係員画面に、開発モードである旨を出し続ける。
終了すると出していた見本はその場で片付き(実際の受付が無ければ待機画面に戻る)、
撮影ブースの欄も消えて撮影画面に戻る。`GET /api/dev/placeholder/:index` は
開発モードでなければ409を返すため、見本が本番に残ることはない。

サーバー側の状態は `devMode` ひとつで、再起動すると必ず解除される。

### 処理履歴と通信監視

処理履歴には、サーバーの処理と各ブースのブラウザでの通信結果が同じ時系列で並ぶ。
HTTPステータスコードとエラー内容も含むため、会場でトラブルが起きたときはここを見る。
ブラウザ側は `logEvent()` (`public/common.js`) から `POST /api/logs` で送っている。

一覧の「内容」は一行で読める長さに保ち、**押すとその下に詳細が開く**。
詳細に出るのは次の4つで、あるものだけが並ぶ。

| 項目 | 中身 |
| --- | --- |
| 発生した場所 | `server.js — Line 766, 5` のように、記録した位置(ファイル名と行・桁) |
| 内容(全文) | 一覧で短くしている分の全文 |
| エラー | `catch` で受け取った例外(stack込み) |
| リクエスト / レスポンス | HTTP通信の要求と応答の全文(JSON) |

発生した場所はサーバー側では `callerLocation()` がスタックから自動で取る。
ブラウザ側は `whereFrom(err.stack)` で取り、`detail.where` として送る。

aging APIとのやり取りは、**一覧には原因だけ**(「APIのユニットが不足しています
(追加購入が必要)」など)を出し、コード・HTTPステータス・APIの原文・要求と
応答の全文は詳細に回す。`describeAgingError()` が短い `summary` と
全文の `full` を返し、一覧には前者、詳細と撮影ブースの係員向けの行には
後者を使う。

**リクエストの `Authorization` は `Bearer ***(伏せ字)` に置き換えてから残す。**
処理履歴は係員画面に出るため、APIキーをそのまま載せない。
1項目あたり4000文字で打ち切る(`DETAIL_MAX_CHARS`)。処理履歴はメモリ上に
最大500件持つため、通信の全文をそのまま溜めると膨らむため。

サーバー側の記録はすべて `addLog()` を通す。`console.log` は使わない。
`addLog()` は警告と異常(`level` が `warn` / `error`)、および
`echo: true` を指定したものを、ホスティング側のログにも流す。
処理履歴はメモリ上にあり再起動で消えるうえ、起動に失敗した場合は
係員画面自体が開けないため、そこだけは二重に残す。
起動は `server:start` として履歴の先頭に残り、`echo` でRenderのログにも出る
(再起動すると保管中の受付と結果が消えるため、「番号が出てこない」の
原因を追えるようにしてある)。

通信状況では、各ブースの画面が今も繋がっているかを確認できる。各ページが
`POST /api/heartbeat` で定期的に生存を伝え、サーバーが最終応答時刻・往復時間・
累計エラー件数を保持する(20秒応答がなければ「応答なし」表示)。
同じ欄にaging APIとの通信結果(直近のステータスコード・成功/失敗件数)も出る。

## セットアップ

```bash
npm install
cp .env.example .env   # AGING_API_KEY に自分のキーを設定する
```

`.env` は `.gitignore` 対象。APIキーをコミットしないこと。
Codespacesでは `.env` を毎回作らずに、Codespaces secrets に `AGING_API_KEY`
を登録しておくこともできる(環境変数が既にあれば dotenv は上書きしない)。

## 起動(Codespaceでの開発)

バックエンド(ポート5000):

```bash
npm start
```

フロントエンド(ポート3000):

```bash
npm run serve:web
```

フロントエンドの配信は必ず `public/` ディレクトリのみを対象にすること。
リポジトリのルートを静的配信(`npx serve` を引数なしで実行)すると、
`.env`(APIキー)・`.git`(コミット履歴)・`uploads`(アップロードされた写真)
まで誰でも取得できる状態になる。

## 公開(Render)

`npm start` だけでフロントエンドとAPIを同一オリジンで配信する。
`server.js` 内の `//NOTE:` コメントで囲まれた箇所が公開用の設定。

CORSは `PUBLIC_ORIGIN` が未設定のとき(=Codespaceでの開発時)だけ有効になり、
許可先もCodespacesの転送URLとローカルホストに限る。公開時は同一オリジン配信
なのでCORSヘッダーを一切付けない。

Renderのダッシュボードで設定する環境変数:

| 変数 | 例 | 用途 |
| --- | --- | --- |
| `AGING_API_KEY` | `sk-...` | aging APIのキー(必須) |
| `PUBLIC_ORIGIN` | `https://aging-demo.onrender.com` | aging APIに渡す画像URLの組み立てに使う |
| `BASIC_AUTH_USER` / `BASIC_AUTH_PASSWORD` | 任意 | 入口のパスワード保護 |
| `APP_BASE_PATH` | `/k7f3m2q8` | 推測困難な公開パス |

ダッシュボードでのコマンド設定:

| 項目 | 値 |
| --- | --- |
| Root Directory | 空欄(リポジトリのルート) |
| Build Command | `npm install` |
| Start Command | `node server.js` |
| Health Check Path | `/healthz` |

**Start Commandは入力欄を一度すべて消してから打つこと。** Renderの入力欄には
`node index.js` のような既定値が入っていることがあり、後半だけを書き換えると
`node start` や `node run start` という命令になる。これは「start / run という
ファイルをNodeで実行しろ」という意味で、本来なら
`Cannot find module '/opt/render/project/src/start'` で起動に失敗する。

この取り違えが起きても展示が止まらないよう、リポジトリ直下に `start.js` を
置いてある(中身は `require('./server.js')` の1行)。`node start` でも
`node start.js` でも起動する。ただし**保険であって正解ではない**ので、
Start Command 自体は `node server.js` に直しておくこと。

Nodeの版は `package.json` の `engines` で `22.x` に固定している。開けておくと
Renderが最新版(26系など)を選び、動作確認していない環境で動くことになる。

同じ内容を `render.yaml` にも置いてあるので、New > Blueprint から
読み込ませれば手入力せずに済む。

上記を設定した場合のアクセス先は
`https://<host>/k7f3m2q8/`(Basic認証あり)になる。
`https://<host>/healthz` だけは認証・公開パスの外でヘルスチェック用に応答する。

### プラン

展示では **Starter(0.5 CPU / 512MB、月$7)** を使う。

無料プランで実際に問題になるのは「15分の無操作で停止する」の一点だった。
次のアクセスで起き上がるまで約1分あり、aging APIがこちらの `/files/:file_id` に
元画像を取りに来る瞬間に止まっていると生成が失敗する。Starterでは停止しない。

CPUはこの用途では効かない。画像の加工はブラウザとaging API側で行い、
サーバーは受け渡すだけ。実測で6人分1周に約0.4秒(TLS込み)で、最も混む
時間帯(120人/時)でも1時間に8秒ぶん。0.1 CPUでも2%程度だった。

**プランを変えても、再起動でデータが消えることは変わらない。**
受付はメモリ上、結果画像はディスク上にあり、Renderはデプロイのたびに
再起動する(環境変数の保存でも再デプロイが走る)。展示中は触らないこと。
